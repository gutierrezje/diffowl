# DiffOwl test usefulness and CI reliability audit

Most of the tests protect useful behavior. The main opportunities are smaller fixtures, reliable process synchronization, and stronger assertions. Broad deletion would remove valuable Git, database, cancellation, and migration coverage while saving little time in the cheap suites.

The last 100 CI workflow runs contain 20 failures, of which 16 involved Windows. This is a history of different changes and their latest run outcomes, **not a measured flake rate**. Several failures were test defects already corrected on main. Others caught real product bugs and should remain covered.

## Scope and evidence

Audited on October 3, 2026. The working checkout was the older `feature/failed-execution-retention` commit `6d90317`, with unrelated documentation edits. For current conclusions, I inspected and tested a clean disposable copy of GitHub main, verified through the GitHub API as **`a18615724f14eb2bf385bafb216d2d2f7973d2f6`**. The inventory below covers all **91 default-discovered test files**, plus the separate verification-controller suite. Historical failures on unmerged branches are identified separately.

- Current main: **1,111 passed, 7 skipped, 0 failed**, 1,118 tests in 91 files; approximately **60.7 seconds** on macOS with Node 22.14.0. Signing was disabled only for the test command.
- The initial sandboxed run had 54 failures, primarily from denied loopback sockets used by execution leases and resulting downstream assertions. The permitted rerun passed. Those local environment failures are not counted as CI defects.
- Separate `test:verification`: **11 passed, 1 failed**. The failing clean-checkout assumption was isolated and reproduced; see below.
- Two deliberately incorrect implementations survived their dedicated test suites. These are narrow mutation experiments, not a whole-suite mutation score.
- A six-pair fixture experiment measured protocol inspection cost. A separate 192-attempt teardown experiment did not reproduce the hosted failure locally.
- CI history: 100 `CI` runs from August 22 through October 3, 2026, retrieved with GitHub CLI; all 20 failed runs had actionable test failures in the retrieved logs. No current linter/build failure was identified in that sample.

Compact run metadata, per-file results, and experiment measurements are saved in [the evidence file](test-suite-and-ci-audit-2026-10-03.evidence.json).

The report contains static review judgments as well as runtime evidence. It does not claim complete branch coverage, a Windows reproduction, a new hosted run, or live model quality verification. No live provider tests were enabled. The production checkout was not changed by the experiments.

## Highest priority findings

### Process teardown has an unnecessarily small test budget

[`src/codex/app-server-peer.test.ts:245`](https://github.com/gutierrezje/diffowl/blob/a18615724f14eb2bf385bafb216d2d2f7973d2f6/src/codex/app-server-peer.test.ts#L245) gives a real child process **3 ms** to shut down. Production divides that budget between stages and then allows a minimum 10 ms for SIGKILL exit. The intended assertion is that a child ignoring SIGTERM is killed and reaped; the test also depends on OS scheduling within a tiny window.

[CI run 34177380054](https://github.com/gutierrezje/diffowl/actions/runs/34177380054) failed here on Ubuntu with `App Server did not exit after SIGKILL`. The same test and budget remain on main. In the local comparison, both 3 ms and 300 ms budgets passed 96/96 attempts, using the same fixture and eight simultaneous children, with budget order alternating between rounds. This confirms local non-reproduction, not absence of the hosted problem.

**Recommendation:** retain the SIGKILL and confirmed-exit assertions, use a realistic process deadline, and always clean up in `finally`. Replace the neighboring fixed 30 ms PID wait with a bounded wait for observed exit. Assertions reading stderr immediately after a stdout reply also deserve synchronization because the streams are independent; that risk was found statically, not in the sampled CI failures.

### The normal protocol fixture creates hundreds of filler files

[`mock-codex-cli.mjs:277`](https://github.com/gutierrezje/diffowl/blob/a18615724f14eb2bf385bafb216d2d2f7973d2f6/src/codex/fixtures/mock-codex-cli.mjs#L277) creates 617 extra TypeScript files and 269 extra JSON files per ordinary inspection. The real compatibility code needs the required schema files and hashes all files; it does not require the synthetic counts. Normal tests nevertheless pin 644 TypeScript and 287 JSON files.

An isolated experiment kept all required schemas and one extra file of each kind. Both versions passed real compatibility inspection, and changing the extra-file content still changed both hashes.

| Fixture | Generated files | Trials | Median inspection time |
| --- | ---: | ---: | ---: |
| Existing | 931 | 6 | 247 ms |
| Required schemas plus two extras | 47 | 6 | 77 ms |

This was about **69% faster for this local operation**, not a measured whole-CI improvement. The fixture is repeatedly used by protocol, executor, and spike suites. A previous Windows run also timed out in protocol hashing, making the extra I/O a credible contributor, although that specific causal link was not reproduced on Windows.

**Recommendation:** shrink the default fixture, retain the extra-file hash regression, and keep a large tree only in an explicitly named scale test if its cost buys a distinct assertion. Do not replace the real process/protocol boundary with a canned success response.

Both mutated source files were restored byte-for-byte after the experiments. Passing these narrow suites does not prove that no other test could catch the mutation. These cases justify strengthening tests, rather than deleting their intended coverage.

### The separate verification suite assumes a dirty source checkout

[`control-diffowl.verification.mjs:212`](https://github.com/gutierrezje/diffowl/blob/a18615724f14eb2bf385bafb216d2d2f7973d2f6/skills/verify-diffowl/control-diffowl.verification.mjs#L212) requires `identity.source.dirty: true` while inspecting the actual source checkout. A clean checkout correctly returns false and fails the test. The isolated clean-checkout reproduction failed in about two seconds with only that field different. Adding one disposable untracked marker made the unchanged test pass; removing it restored the clean checkout.

**Recommendation:** compare with explicitly captured source state, or construct a disposable source fixture and deliberately test clean and dirty states. This suite has valuable ownership, evidence, cancellation, and cleanup checks, but it must not depend on a developer having unrelated uncommitted work. It is not selected by the current CI workflow, so this is a newly reproduced local test defect, not an explanation for the sampled hosted failures.

### Fixture isolation and coverage gaps need targeted work

- **Git policy leaks into fixtures.** Several helpers still inherit signing, hooks, and relevant Git configuration. Earlier CI failures involved initial branch assumptions, merge direction, Windows path aliases, and line endings. Centralize disposable repository setup with an explicit branch and identity, signing off, isolated hooks, and deliberately chosen line-ending policy. Do not alter global user settings.
- **Journal coalescing uses a real one-second clock.** A scheduler pause can legitimately trigger a flush between two records that the test expects to coalesce. Use the available injected clock and explicitly advance it for expiry tests. Preserve real SQLite contention/deadline coverage separately; widening a three-second ceiling beyond the five-second bad behavior would weaken that regression.
- **Cursor parent tests bypass the actual SDK worker.** The executor tests inject a mock worker; a test called a bounded validation retry consumes a canned retry event. Keep the process/IPC checks, but add an offline test of the real worker with a scripted SDK boundary for retries, cancellation, tool policy, and disposal. This gap is not evidence of a current SDK failure.
- **Production and experimental Windows port parsers differ.** The experimental helper rejects port 40960 when looking for 4096. Production `opencode/server.ts:383` uses a substring match and can accept it. Existing server fixtures do not cover this case. This is a source-confirmed coverage gap and potential wrong-listener defect, not a sampled CI failure; test the production selection path.
- **Live eval selection is implicit.** Ordinary discovery enables `eval/runner.integration.test.ts` whenever `DIFFOWL_EVAL_MODEL` is set. Use a separately selected live project/script and explicit opt-in. It was skipped in this audit and is not blamed for the sampled CI failures.

## What to keep and what to consolidate

The strongest coverage exercises real Git targets and worktrees, database upgrades and rollback, durable finding identity/lifecycle, read-only readiness, cancellation ownership, output schemas, and review-document acceptance. Keep those regular offline checks. Fake provider output is appropriate when the test's claim concerns persistence or transport rather than model judgment.

Consolidation candidates are literal package-script spelling, duplicated prose/history assertions, overlapping status-only output cases, and repeated equivalent topology setup. They are maintenance costs, not demonstrated intermittent failures. Pure output and OpenCode tests are very cheap in the measured run; deleting them is unlikely to materially improve CI duration.

The CLI integration file took about **58.9 seconds**, almost the full 60.7-second wall time. Codex runner, protocol, readiness and context were the other substantial files, running concurrently. Preserve CLI journeys that prove command wiring and persisted state. Split the large file by independent feature to improve diagnosis and scheduling only after moving its build setup to one shared step. Currently its `beforeAll` builds the CLI, and CI builds again after tests. Avoid multiplying that build when splitting files.

## Recommended implementation order

1. Stabilize process fixtures: realistic teardown bounds, readiness/exit synchronization, unconditional cleanup, and isolated repository inputs for runner tests. Keep a real deadline/kill smoke test alongside deterministic policy tests.
2. Shrink ordinary protocol generation and the 40-commit reachability fixture where only three distinct candidate invocations are asserted. Measure the full Linux/Windows matrix before claiming a CI speedup.
3. Standardize disposable Git settings and clock control. Separate pure tests, offline process/database integrations, and explicit live-provider checks. Evaluate worker limits for the integration group with measurements; do not serialize the whole suite or add blanket retries by default.
4. Repair the demonstrated weak assertions and the clean-checkout verification test. Add the real Cursor worker contract and production Windows port-parser case.
5. Consolidate cheap duplicates only when touching those files; prioritize useful failure signals over reducing test counts. Retain the Windows job, which caught real product problems.

These are recommendations from an audit. Product/test-suite implementation, commits, pushes, and hosted CI reruns were not performed. A follow-up should carry the chosen fixes through focused regressions, the full appropriate matrix, and the repository review process.
